## 1. 지금 코드가 "길은 한 줄"이라고 가정하는 곳

| 파일 · 함수 | 지금 하는 일 | 한 줄 길 가정 |
|---|---|---|
| `js/data/map.js` `PATH_TILES` | 꺾이는 칸 13개로 된 배열 하나 | 입구 하나에서 왕좌까지 꺾은선 하나 |
| `map.js` `PATH` (`buildPath`) | `segments`, `length`, `cells`를 한 번만 만듦. `points[0].x = -60`으로 문 밖에서 걸어 들어옴 | 전역 객체 하나이고, 입구 보정도 첫 점에만 함 |

## 2. 게임 방식 후보

| 후보 | 생김새 | 플레이어가 고민할 것 | 구현 비용 |
|---|---|---|---|
| A. 합류형 | 입구 두 개가 중간 칸에서 합쳐진 뒤 왕좌까지 같이 감 | 합류 전에는 갈래마다 따로 막을지, 합류 뒤 한곳에 모을지. 두 갈래 사이에 낀 칸의 가치가 높아짐 | 중간. 갈림 판단이 없음 |
| B. 분기형 | 한 길이 중간에 둘로 갈렸다가 다시 합쳐짐. 용사가 갈림길에서 고름 | 어느 쪽으로 몰릴지 읽어야 함. 길막기로 다른 쪽에 몰아넣는 판단이 생김 | 큼. 고르는 규칙과 경로 탐색, 예고가 다 필요함 |
| C. 웨이브마다 입구 교체 | 입구가 둘이지만 웨이브 한 번에 한쪽만 열림 | 다음 웨이브 입구를 보고 미리 짓거나 옮겨 지음 | 작음. 대신 동시에 압박하는 맛이 없음 |

## 3. 추천: A 합류형

- 이유: 용사가 고를 일이 없으므로 "길 = 미리 정한 꺾은선"이라는 지금 구조를 그대로 둘 수 있습니다. 판단은 "어디에 나눠 지을까"로 분명해집니다.
- B는 A를 끝낸 뒤 "갈래를 고르는 규칙"만 더하면 넓힐 수 있습니다(경로 목록이 이미 있으므로).

### 데이터 구조

```js
// map.js: 입구별로 왕좌까지 가는 꺾은선 전체를 적는다. 합류 뒤 칸은 같다.
const ROUTES_TILES = {
  north: [[0,3],[4,3],[4,7],[8,7],[8,3], ...공통],
  south: [[0,9],[8,9],[8,7],[8,3], ...공통],
};
const ROUTES = { north: buildPath(tiles), south: buildPath(tiles) }; // 기존 buildPath를 함수로 뺀다
const PATH_CELLS = 모든 경로 cells의 합집합;
pathAt(routeId, d); nearestPathPoint(x, y) -> { route, d, x, y };
```

- 용사: `h.route`를 추가하고, `heroWorld`와 도착 판정은 `ROUTES[h.route]`를 씁니다.
- 시체와 타락 유닛: `route`와 `d`를 같이 저장합니다(지금 `d`는 읽는 곳이 없으니 필요 없으면 지워도 됩니다).
- 웨이브 데이터: `WAVES[i].entry`를 추가합니다(예: `{ north: 0.5, south: 0.5 }` 비율이나 직업별 지정). 형식은 사용자 결정이 필요합니다.
- `PATH`는 1차 PR에서 `ROUTES.north`의 별칭으로 남겨 두어 한 번에 다 깨지지 않게 합니다.

## 4. 갈래 길에서 판정 규칙

| 항목 | 규칙 |
|---|---|
| 가장 앞선 용사 | `h.d`를 비교하지 않고 **남은 거리** `ROUTES[h.route].length - h.d`가 가장 작은 용사를 고릅니다. 합류 뒤 구간은 두 길이 같으므로 값을 서로 비교할 수 있습니다. 같으면 지금처럼 먼저 찾은 쪽 |
| 오크 길막기 집결점 | `nearestPathPoint`가 가장 가까운 길의 `{route, d}`를 돌려줍니다. 합류 뒤 구간이면 어느 길이든 같은 좌표입니다. 거리가 같으면 `north`를 먼저 씁니다. `createOrc`는 `pathAt(rally.route, rally.d ± 42)`를 씁니다. 붙잡는 판정(`nearestHero`)은 좌표로 하므로 바꾸지 않습니다 |
| 집결점이 합류점 근처일 때 | `d ± 42`가 합류점을 넘으면 오크 한 마리가 다른 갈래를 비울 수 있습니다. 1차는 그대로 두고, 직접 해 보고 고칩니다 |
| 건설 칸 | `isPathCell`이 합집합을 보게만 하면 `BUILD_CELLS` 코드는 그대로입니다. 두 갈래 사이에 낀 칸은 저절로 "양쪽에 닿는 칸"이 됩니다 |
| 파티 예고 | "다음 파티" 창에 입구별로 줄을 나눕니다(예: `북 전사2 궁수1 / 남 사제1`). 준비 시간에는 입구 문 위에 인원 표시를 띄웁니다. 보스가 오는 입구도 따로 표시합니다 |
| 출발 간격 | `spawnGap`을 입구마다 따로 셉니다. 두 입구가 동시에 출발하면 압박이 두 배가 되므로 엇갈릴지는 사용자 결정이 필요합니다 |

## 5. 이전 맵에 넣었던 예시 (26x15, 건설 가능 줄 2~10. 지금 맵은 맨 위 구현 상태 표)

- 북쪽 길(지금 그대로): `[0,3] → [4,3] → [4,7] → [8,7] → [8,3] → …(지금과 같음) → [23,7]`
- 남쪽 길(새로 넣음): `[0,9] → [8,9] → [8,7] → [8,3] → [12,3] → [12,8] → [16,8] → [16,4] → [20,4] → [20,10] → [23,10] → [23,7]`
- 합류점: `(8,7)`. 지금도 꺾이는 칸이므로 T자 바닥을 그리기 쉽습니다.
- 새로 생기는 길 칸: `(0..8, 9)`, `(8, 8)`. 장식 `(2,10)` 수정과 화로 `(1,10)`과 겹치지 않습니다.
- 낀 칸: `(5..7, 8)`. 북쪽 줄 7과 남쪽 줄 9 사이에 있어 두 갈래를 다 칠 수 있는 칸입니다.
- 길이: 합류까지 북쪽은 12칸, 남쪽은 10칸입니다. 남쪽이 2칸 짧아서 같이 출발하면 남쪽이 먼저 도착합니다.
- 비어 있던 왼쪽 아래(열 0~3, 줄 5~10)가 건설 칸으로 바뀝니다. `BUILD_CELLS` 개수는 지금보다 늘어납니다(재지 않음).

## 사용자 결정 필요

- 후보 A(합류형)로 갈지, 처음부터 B(분기형)를 목표로 할지
- 입구 배분을 비율로 할지, 웨이브마다 직업별로 정해 적을지
- 두 입구가 동시에 출발할지, 엇갈려 출발할지. 보스는 어느 입구로 올지
- 남쪽 길이 2칸 짧은 것을 그대로 둘지(남쪽 압박이 셈), 길이를 맞출지
- 1지역에 바로 넣을지, 다음 지역 맵에서 처음 보여 줄지
- 늘어난 건설 칸을 `BUILD_REACH` 등으로 줄일지
- 둘째 입구 문 그림을 새로 만들지(PixelLab), 지금 그림을 다시 쓸지
